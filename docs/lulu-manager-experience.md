# Make a Lulu order easier to release

**Manager experience review, 26 November 2026.** A manager with a paid ticket should have one decision to make after the customer review period: “Are these the reviewed files, going to this person, for this total?” Today the ticket has most of that information. The manager still has to connect the proof version, email, reply inbox, supplier quote and two different order statuses. A new staff order adds a blank address form and a second screen.

The [operator guide](how-to/submit-a-lulu-print-order.md) describes current behavior and includes the production screenshots. Everything under **Proposed experience** below is a recommendation.

## Where managers lose time today

| Point in the workflow        | Evidence and impact                                                                                                                                                                                                                                                                                                                                                              |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Finding the right request    | The production list showed two open print tickets for the same story. Subjects emphasized story IDs. One was Admin-initiated and the other had a purchaser proof. Starting again from the story creates another independent request. A manager needs the title, order reference, purpose and supplier state before clicking **Open**.                                            |
| Starting a print             | A standard story says **Order Print & Ship via Lulu** and a premium story has both a dispatch form and a staff-proof form. The generic panel also offers a manual provider. Its first button creates and prepares; dispatch happens on another page. Its success text can say “prepared” even when the server returns a preparation warning.                                     |
| Entering delivery data       | On the live standard story form seven contact/address fields are mandatory for a typical PT shipment; ten are visible. The country comes after the region. Tax ID is shown for Portugal as well as for countries that require it. A legacy upgrade can prefill an author's details while the parcel may be a gift. The two staff forms enforce different input lengths at entry. |
| Proof and release            | Production tickets showed two proof links, a quote, an acknowledgement and an empty amount input. Staff must compare versions, check a separate mailbox, and copy the price. A new provider or corrected address can invalidate that work. There is no ticket-native customer review deadline or linked reply disposition in the reviewed flow.                                  |
| Understanding completion     | A live customer ticket combined **Open**, **submitted** and Lulu **CANCELED**. Another submitted Admin order still displayed the prepare button and price-entry controls. A disabled submit button gives little guidance when the manager's real task is tracking, payment or handling a cancellation.                                                                           |
| Recovering from an exception | The current adapter can turn a changed address suggestion into a hold, without presenting the suggested fields side by side. A price or shipping change requires action. An uncertain create requires reconciliation. Each calls for a different next action, and creating a new order can compound the problem.                                                                 |

Accessibility concerns to validate with managers and assistive technology include whether a keyboard user can find the reason for a disabled release action, whether a screen reader announces a new state during polling, and whether a region or tax-ID error takes focus to the right field. Screenshots establish visible layout only.

## Proposed experience

### 1. Give each request one recognizable home

Add **Print orders** as a saved view of Tickets. Show book title/thumbnail, order reference, purpose (customer shipment, staff proof or Admin shipment), quantity, destination country, latest supplier status and **Next action**. Group by needs attention, awaiting customer review, ready to send and with supplier. Keep global pricing/provider configuration behind **Print settings**. Changing a default must remain separate from releasing one order.

Use one **Order a printed copy** entry point on a story. Start with **One staff proof** or **Print and ship**. Preselect the published edition, binding and quantity. Keep the revision-based proof deduplication. Before creating another general order, offer an existing matching request and require explicit intent for a genuinely new shipment. Persist a creation intent across reloads and timeouts. Do not deduplicate legitimate repeat orders solely by story.

### 2. Ask only for information Mythoria does not have

For paid orders show a read-only delivery card from the order snapshot with **Correct address**. For Admin orders offer a saved staff destination, a confirmed customer address, or **Someone else**. Display who supplied the address and which person receives proofs. Require a deliberate choice before substituting the author's address for a gift recipient. Show the full address for final review. Limit storage and visibility of country-specific tax IDs.

Put country first, present localized country and region names while saving codes, and reveal subdivision and tax fields only when applicable. Make line 2 optional and expandable. Validate lengths inline before queuing expensive rendering. Run Lulu's address/cost preflight as soon as the necessary product and address data are ready. Show **Entered** and **Suggested** for a material change, identify the changed field and record the customer's confirmation. Only normalize defined, equivalent formatting automatically. [Lulu address validation](https://help.api.lulu.com/en/support/solutions/articles/64000305072-address-validation)

### 3. Prepare automatically, then present one explicit purchase decision

Keep the existing worker, file identities, QA and ticket. After provider selection or a confirmed correction, prepare and quote once for that exact version and show progress in place. For paid orders wait for the current proof email. Show the proof pair side by side, with version, revision and sent time. Put the shipping address, binding, copies, tracked service, tax-inclusive total and per-copy cost together. Show the full cost breakdown on demand.

When eligible, propose a single action such as **Submit 2 copies to Lulu · €31.40**. Carry the displayed amount and quote identity in the confirmation instead of making the manager type the amount again. Keep explicit human confirmation, the audit record, live re-quote, file identity checks, ceiling and single-submission guard. A changed quote or proof invalidates the earlier confirmation and shows exactly what changed. An elapsed timer, a customer approval, or a provider default must never purchase a print job.

### 4. Bring customer review and exceptions into the ticket

Add the purchaser email's order reference, proof version and review deadline to the timeline. Offer **Report a problem** from the proof email, and route replies to the matching ticket/version. An objection should place the ticket on hold and notify its owner. An unmatched reply should go to a staffed queue. Show **No reply recorded by [time]** separately from affirmative customer approval. Make the review period a business setting and preserve a manual mailbox check until reply ingestion is proven reliable.

For failed preparation show one remedy, such as **Correct address**, **Review new quote**, **Retry file preparation** or **Contact print support**. Announce status changes to assistive technology, show blocking reasons in text near the primary action, and focus the first invalid field. When the supplier outcome is uncertain, reconcile the existing job and suppress all new-create actions for that intent until resolved.

### 5. Replace release controls with fulfillment follow-up after submission

Show the three state histories with plain labels: **Customer support**, **Mythoria release**, **Lulu production**. After submission replace review controls with the supplier job link and relevant action: **Check supplier payment**, **View tracking**, **Check cancellation**, or **Investigate delivery**. Reuse webhook/poll reconciliation and surface its last successful update. A confirmed cancellation should clearly say whether a customer refund or replacement still needs attention. Keep supplier quote, recorded supplier cost and actual settlement distinct.

Add localized shipment/exception notifications deduplicated by job and shipment, plus an explicit replacement that links back to the original order and proof. Keep **Buy another copy** separate from a staff-issued replacement. A supplier auto-pay setting may streamline payment after a manually approved release, but adoption is a finance decision for the Lulu account owner. [Lulu Developer Portal](https://developers.lulu.com/)

## Delivery order and measures

| Priority | Ship first                                                                                                                                                                                                | How to know it worked                                                                                                                                                                                                                 |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1        | Ticket list with title, order purpose and next action. State-specific ticket footer. Direct handoff to the existing ticket after creation, with accurate “created / preparing / needs attention” wording. | On a submitted/canceled ticket, a manager can identify the supplier outcome and next action without seeing an editable price field. Measure wrong-ticket opens and duplicate requests.                                                |
| 2        | Single entry point, creation-intent deduplication, saved staff destinations, country-aware fields and address comparison.                                                                                 | Repeat a staff shipment to a saved address without retyping contact details. Retrying after a timeout recovers the same request. Measure fields manually entered, rejected addresses and time to a valid quote.                       |
| 3        | Proof, delivery and price review on one screen with one explicit priced release. Linked proof replies and holds.                                                                                          | On a ready paid order, staff enter zero shipping fields and zero price digits. A changed version, changed quote, open objection or over-ceiling total blocks release. Two simultaneous confirmations create at most one supplier job. |
| 4        | Payment/tracking alerts, customer updates and linked replacements.                                                                                                                                        | Managers distinguish unpaid, in production and canceled at a glance. Measure unpaid age, uncertain-job age, tracking enquiries and time to resolve a failed shipment.                                                                 |

Before rollout, baseline active handling time separately for a paid order, a new staff shipment and a correction. Exclude customer waiting time and supplier manufacturing time. Run the same tasks with managers in a sandbox using fictional recipients, including an address correction, changed price and timeout after create. Report outcomes and duplicate-job counts alongside time saved. This review measured neither task times nor conversion rates.
